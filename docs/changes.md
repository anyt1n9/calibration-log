# 仕様書から変えた点と、その理由

`spec.md` を実装したときに判断した差分。バランスや見せ方を触る前にここを読むこと。

---

## 1. 判定時の「一言メモ」を入力UIにしなかった

**仕様**: `note` フィールドを持ち、判定時に任意で一言を添えられる。

**実装**: データ構造には `note` を残したが、入力欄は置いていない。判定は ○ / ✕ / 判定できない の3ボタンだけ。

**理由**: 答え合わせは3秒で終わらなければならない。テキスト欄があると「何か書かなければ」という圧力が生まれ、判定そのものを後回しにする。書きたくなったら足せばよいが、最初から置くと核が鈍る。

---

## 2. 曲線の点を線でつないだ

**仕様**: 点と誤差帯のみ。

**実装**: 隣り合う点を淡い線（不透明度35%）でつないだ。

**理由**: 5点が独立していると「形」が読めない。自信過剰なら右下に垂れる、という全体の傾向は線があって初めて見える。ただし濃く描くと点を繋いだ線自体が意味を持つように見えるので、目立たせていない。

---

## 3. 判定件数（n）を点の真下に置いた

**仕様**: 特に指定なし。

**実装**: 当初はバケットの中央（55, 64.5, …）に置いたが、点は平均確信度の位置（例: 90-100バケットなら92.3）に描かれるため、ラベルと点が横にずれて対応が読めなかった。データがあるバケットでは点と同じx座標に置いている。

---

## 4. 延期は7日固定にした

**仕様**: 「延期は可、記録に残す」とだけ書いてあった。

**実装**: 「7日延ばす」の1ボタン。日数は選べない。

**理由**: 延期の日数を選ばせると、それ自体が判断になって時間を取る。延期は逃げ道であって機能ではないので、最小の操作に留める。3回を超えると「判定から逃げていませんか」と出る。

**起点は今日**（8番で修正）。元の期限と今日の遅いほうに7日を足す。

---

## 5. 表示テーマの切り替えボタンを足した

**仕様**: ダークモード対応とだけ。

**実装**: ヘッダーに「自動 / 明 / 暗」を巡回するボタン。設定は localStorage に保存。

**理由**: OSの設定に従うだけだと、明暗どちらでも破綻していないことを確認する手段がない。開発中の検証にも使える。

---

## 6. 保存フラグを ref から reducer の state に移した（バグ修正）

**当初の実装**: `useRef` で「読み込み済みか」を持ち、読み込みエフェクトの中で `true` にしていた。

**起きたこと**: **リロードすると全データが消えた。**

React は宣言順にエフェクトを実行する。読み込みエフェクトが `hydrated.current = true` を立てた直後、同じコミットで保存エフェクトが走る。このとき `state.predictions` はまだ初期値の空配列なので、**空配列が本物のデータを上書きする**。dispatch による再レンダリングは、その後に来る。

**修正**: `loaded` を reducer の state に持たせ、`hydrate` アクションで `true` にした。保存エフェクトは `state.loaded` を見る。これならフラグの更新と予測データの更新が同じ再レンダリングで届くため、順序がずれない。

**教訓**: 「読み込みが終わったか」を ref で持つと、エフェクトの実行順に依存した罠になる。レンダリングに反映されるべき状態は state に置く。

---

## 7. 開発用のダミーデータは意図的に自信過剰にした

`src/lib/sample.ts` は、確信度が高いほど実際の的中率とのズレが大きくなるよう生成している（`drift = (確信度 - 50) / 50 * 22`）。

**理由**: 曲線が正しく描けているかは、歪んだデータを入れないと確認できない。ランダムに生成すると点が理想線の周りに散らばり、バグと正常の区別がつかない。

乱数は固定シード（20260920）なので、毎回同じデータが出る。

---

## 8. 数字が嘘をついていた3か所を直した（バグ修正）

**入力画面の説明が95%を「確実」と言っていた**: 「10回同じことを言ったら{確信度÷10を四捨五入}回当たる」と出していたため、95〜99% が「10回中10回」になっていた。95%は確実ではない、を教えるアプリが入力画面で逆のことを言っていた。「100回同じことを言ったら95回当たり、5回外れる」に変えた。外れる回数も並べるのは、高い確信度でも外れる余地があることを入力の時点で見せるため。

**延期が元の期限を起点にしていた**: 期限を10日過ぎた予測を延期しても3日過ぎのまま判定待ちに残り、押し直すたびに延期回数だけが増えて、すぐに「判定から逃げていませんか」が出た。逃げた回数を見せる仕組み（仕様 3-3）が、逃げていない回数まで数えていた。今日を起点にした。

**判定日がUTCで表示されていた**: `resolvedAt`（ISO8601、UTC）の先頭10文字を日付として表示していたため、日本時間 0:00〜8:59 の判定が前日の日付で履歴に出ていた。端末のタイムゾーンで日付にする `dayOf()` を `src/lib/date.ts` に足した。保存形式は変えていない。

---

## 9. 記録を失う経路を塞いだ

**ホーム画面に追加を案内する**: Safari は、7日間操作のなかったサイトの localStorage を消すことがある。期限が数週間先の予測を置いて開かずにいるのが普通の使い方なので、記録ごと消えかねない。ホーム画面（Mac は Dock）から開くアプリにはこの削除が掛からないため、Safari で普通に開いているときだけホームの最下段に案内を出す。閉じたら二度と出さない。単独のアプリとして開けるよう、`public/` にマニフェストとアイコンを足した。

- 最下段に置いたのは、判定待ちと入力の邪魔をしないため（仕様 2）
- 追加したアプリには記録が引き継がれないことがあるので、記録があるときは書き出し→読み込みの手順も添える
- 書き出しの催促や `navigator.storage.persist()` も候補に挙げたが、まずは案内だけにすると決めた

**複数タブの上書き**: 保存は毎回全件を書き戻すので、タブAで足した予測を、古い全件を持ったタブBの保存が消していた。`storage` イベントで他のタブの変更を取り込む。壊れた値や消去は取り込まない（空配列で手元の記録まで消さないため）。

**ストレージ例外で真っ白**: サイトデータをブロックする設定では、localStorage に触れただけで例外が出る。テーマ設定の読み書きだけ守られておらず、起動時に全体が落ちていた。読み書きはすべて `src/state/storage.ts` を通すようにした。あわせて、描画中の例外で真っ白にならないようエラー画面を置き、保存されている中身をそのまま書き出せるようにした。真っ白だと、記録が消えたと思ってブラウザのデータを消しかねない。

**読み込みの検証**: 確信度は 50〜99 の整数（仕様 3-2）、判定は hit / miss / void / なし、期限は実在する日付、作成日時は日時として読めること、を確かめる。通らない1件と、id が重複した2件目以降は読み込まず、件数を確認ダイアログに出す。以前は `outcome` が想定外の値だと記録タブが落ち、範囲外の確信度は曲線を壊していた。
