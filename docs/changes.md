# 仕様書から変えた点と、その理由

`spec.md` を実装したときに判断した差分。バランスや見せ方を触る前にここを読むこと。

---

## 1. 判定時の「一言メモ」を入力UIにしなかった

**仕様**: `note` フィールドを持ち、判定時に任意で一言を添えられる。

**実装**: データ構造には `note` を残したが、入力欄は置いていない。判定は ○ / ✕ / 判定できない の3ボタンだけ。

**理由**: 答え合わせは3秒で終わらなければならない。テキスト欄があると「何か書かなければ」という圧力が生まれ、判定そのものを後回しにする。書きたくなったら足せばよいが、最初から置くと核が鈍る。

---

## 2. 曲線の点を線でつないだ

**仕様**: 点と誤差帯のみ。

**実装**: 隣り合う点を淡い線（不透明度35%）でつないだ。

**理由**: 5点が独立していると「形」が読めない。自信過剰なら右下に垂れる、という全体の傾向は線があって初めて見える。ただし濃く描くと点を繋いだ線自体が意味を持つように見えるので、目立たせていない。

---

## 3. 判定件数（n）を点の真下に置いた

**仕様**: 特に指定なし。

**実装**: 当初はバケットの中央（55, 64.5, …）に置いたが、点は平均確信度の位置（例: 90-100バケットなら92.3）に描かれるため、ラベルと点が横にずれて対応が読めなかった。データがあるバケットでは点と同じx座標に置いている。

---

## 4. 延期は7日固定にした

**仕様**: 「延期は可、記録に残す」とだけ書いてあった。

**実装**: 「7日延ばす」の1ボタン。日数は選べない。

**理由**: 延期の日数を選ばせると、それ自体が判断になって時間を取る。延期は逃げ道であって機能ではないので、最小の操作に留める。3回を超えると「判定から逃げていませんか」と出る。

---

## 5. 表示テーマの切り替えボタンを足した

**仕様**: ダークモード対応とだけ。

**実装**: ヘッダーに「自動 / 明 / 暗」を巡回するボタン。設定は localStorage に保存。

**理由**: OSの設定に従うだけだと、明暗どちらでも破綻していないことを確認する手段がない。開発中の検証にも使える。

---

## 6. 保存フラグを ref から reducer の state に移した（バグ修正）

**当初の実装**: `useRef` で「読み込み済みか」を持ち、読み込みエフェクトの中で `true` にしていた。

**起きたこと**: **リロードすると全データが消えた。**

React は宣言順にエフェクトを実行する。読み込みエフェクトが `hydrated.current = true` を立てた直後、同じコミットで保存エフェクトが走る。このとき `state.predictions` はまだ初期値の空配列なので、**空配列が本物のデータを上書きする**。dispatch による再レンダリングは、その後に来る。

**修正**: `loaded` を reducer の state に持たせ、`hydrate` アクションで `true` にした。保存エフェクトは `state.loaded` を見る。これならフラグの更新と予測データの更新が同じ再レンダリングで届くため、順序がずれない。

**教訓**: 「読み込みが終わったか」を ref で持つと、エフェクトの実行順に依存した罠になる。レンダリングに反映されるべき状態は state に置く。

---

## 7. 開発用のダミーデータは意図的に自信過剰にした

`src/lib/sample.ts` は、確信度が高いほど実際の的中率とのズレが大きくなるよう生成している（`drift = (確信度 - 50) / 50 * 22`）。

**理由**: 曲線が正しく描けているかは、歪んだデータを入れないと確認できない。ランダムに生成すると点が理想線の周りに散らばり、バグと正常の区別がつかない。

乱数は固定シード（20260920）なので、毎回同じデータが出る。

---
